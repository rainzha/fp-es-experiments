# Chapter 1 反思 — 领域校验的两层模型（编译期 vs 运行时）

## 核心区分
领域合法性约束分为完全不同的两层：

1. **ADT / 密封类型校验（编译期）**
用于限制**业务状态的变体集合**，在编译阶段锁定合法状态，让非法状态**根本无法定义、无法构造**。

典型场景：游乐设施状态只能是「在线 / 离线」。
通过 F# 可区分联合、Java 密封接口，编译器直接禁止出现第三种非法状态。
这就是 FP 核心思想：**让非法状态不可表达**。

2. **字段业务规则校验（运行时）**
诸如「最小年龄不能为负数」「名称不能为空」这类**字段数值范围、格式、长度约束**，
属于**业务不变量（Domain Invariant）**。

**无论 F#、Java、Elixir，这类规则全都必须运行时校验**。
ADT 只能管「有哪些状态」，**管不了字段内部数值是否合法**。

## 两层防御的标准 FP-DDD 建模方案
1. **编译期防护（ADT）**
用代数数据类型锁定有限的业务状态、分类、变体，从类型层面杜绝非法枚举状态。

2. **运行时防护（工厂校验）**
通过私有构造器 + 工厂函数做数值校验，
失败返回错误值（Either / Result），**不用异常中断程序**。

## 三种语言的差异总结
- **F# / Java sealed**：一部分非法状态在编译期直接消灭；字段数值规则仍需运行时校验。
- **Elixir（动态类型）**：**没有任何编译期约束**，所有领域合法性全部依赖运行时校验函数。

## 最终结论
ADT 解决的是 **“非法状态能否存在”** 的问题（编译期）。
业务字段规则解决的是 **“合法状态下的值是否合规”** 的问题（运行时）。

即使是强类型 FP 语言，也无法用类型系统完全替代业务运行时校验。

# Chapter 1 反思 — 错误作为值：{:ok, value} 与专用返回类型对比

## Elixir 的方案：`{:ok, ride} | {:error, reason}`
Elixir 没有内置的专用结果类型，依靠**固定格式的二元元组**表达成功或失败。
这是一套社区约定的编程规范，不是编译器强制的类型。
调用方必须手动模式匹配这个元组来处理成功和失败分支。

## 其它静态函数式语言的专用类型
- **F#**：`Result<'Success, 'Error>`
- **Java(Vavr)**：`Either<L, R>`
- **Rust**：`Result<T, E>`

它们是**语言/库层面定义的代数数据类型**，拥有一套配套的高阶函数：`map`、`flatMap`、`bind` 等，方便链式组合校验逻辑。编译器会强制我们处理错误分支。

## 共同点（核心思想完全一致）
1. 错误不再是抛出中断程序的异常；**错误本身就是普通返回值**
2. 使用模式匹配区分成功场景与失败场景
3. 支持链式组合多个校验步骤，实现铁路式编程

## 细微差异
1. Elixir：动态语言，二元组只是约定，编译器不会强制校验返回格式；组合逻辑需要自己封装函数。
2. F# / Rust / Vavr‑Java：静态类型 + 专用结果类型，自带完整的函数式算子，编译期约束返回类型，工具链更完善。

## 个人感受
从开发体验上来说，我更喜欢 `Result / Either` 这种独立专用类型的设计。
但二者底层设计理念高度同源，工程能力差距并不大，只是语法与语言生态带来的表层区别。


## Chapter 1 反思 — 构造时的默认值处理方案对比

## Elixir 的实现方式
使用关键字列表 `opts` + `Keyword.get(key, fallback)` 实现可选参数与默认值。
1. 调用方只需要传入必要字段，其余字段自动填充预设默认值
2. 属于运行时动态读取配置，语言原生支持这套灵活的可选参数风格
3. 默认值写在构造逻辑内部

```elixir
min_age: Keyword.get(opts, :min_age, 0)
```

## F# 的常规做法

F# 本身没有内置的「可选参数带默认值」的便捷语法，主流两种方案：

1. **重载多个 create 函数**
`create(name)` / `create(name, minAge)`
2. 使用**可选参数 `option` 类型**，在函数内部手动提供后备值

```
let create(name, ?minAge) =
    let realMinAge = defaultArg minAge 0
    // ...
```

默认值依然由业务代码显式定义，不是类型自带。

## Java（Record + Vavr）原生特性

Java Record **不能直接定义字段默认值**。
我们只能通过**多个静态工厂方法**来模拟默认行为：

1. `create(String name)` // 全部使用默认配置
2. `create(String name, int minAge)` // 自定义部分字段

或者使用 Builder 模式封装默认值逻辑。
Record 本身只是数据载体，不保存任何默认规则；默认逻辑全部写在应用层的工厂函数里。

## 三者本质共同点

**数据结构本身不会携带默认值规则。默认值是构造函数 / 工厂函数的业务逻辑，不属于类型本身。**

## 差异小结

1. Elixir：关键字列表让「部分传参」写法最简洁自然，适合快速灵活的构造。
2. F#：依靠 `defaultArg` 或者多函数重载实现。
3. Java：通过多静态工厂 / Builder 手动实现默认填充。

# Advanced Functional Programming with Elixir · Chapter 1 Reading Notes

# 1. DMMF从一开始就用F#代数类型锁定合法状态；Elixir依靠 struct + 构造函数约束建模。动态语言如何规避非法领域对象？
1. 唯一对外暴露合法入口：私有保护构造逻辑
业务代码不允许直接用`%Module.Struct{field: raw}`随意赋值，强制通过`make/2, make/4`这类命名构造器创建实例。

2. 守卫子句 + 运行时前置校验
利用Elixir `when`守卫做基础类型与业务不变量校验（年龄>0、身高>0）；复杂业务规则在函数内部判断，失败返回错误元组 `{:error, reason}`。

3. 社区契约约束（规范而非编译器强制）
Elixir是动态语言，编译器无法阻止外部绕过构造器手动构造非法struct，依靠团队编码规范、单元测试、属性测试保证不生成非法对象。

4. 纯不可变数据
一旦构造完成，没有setter修改字段；变更只能调用业务函数返回全新结构体，避免运行中对象状态被篡改。

> 对比F#：F#的ADT是**编译期锁死合法状态**；Elixir是**运行时校验 + 工程规范**来保护领域不变量。

# 2. 对比Java值对象（Record + 私有构造 + 静态工厂）和Elixir Struct建模风格的异同
## 相同点
1. **不可变性**：Java Record天然不可变；Elixir struct默认不可变，修改只能生成新实例，符合DDD值对象设计原则。
2. **受控创建**：都使用静态工厂/`make`命名构造函数，把校验逻辑收拢在唯一创建入口，防止外部直接new/字面量构造非法实例。
3. **结构化数据载体**：只承载领域数据，承载业务不变量校验。

## 差异点
|维度|Java Record(静态OOP)|Elixir Struct(FP动态)|
|---|---|---|
|类型安全|编译期校验字段类型|运行时校验，编译器不做类型检查|
|访问权限|可以私有化构造器，彻底禁止外部new|语法层面无法禁止字面量`%Mod.Struct{}`，依赖人为规范|
|行为放置|业务行为可以写在Record内部方法|**数据与行为分离**，业务函数写在模块独立函数，不属于结构体本身|
|相等判断|Record自动实现equals/hashCode|Elixir结构体原生基于值对比相等|

# 3. DDD通用语言(Ubiquitous Language)在FunPark案例中如何体现？和你Java项目里 Command / UseCase / ValueObject 命名规范对照
1. **FunPark案例里的统一语言**
领域名词直接作为代码命名：`Patron`游客、`FastPass`快速通行券、`Ride`游乐项目。
业务概念和代码命名完全对齐，产品、业务、开发人员沟通使用同一套词汇；业务规则直接使用领域名称编写函数（例如发放快速券、校验准入资格）。

2. **和Java六边形架构项目对照**
- FunPark：**领域实体/值对象命名**：Patron、FastPass、Ride
- Java工程分层命名：
  - `Command`：外部传入的输入指令（应用层入参）
  - `UseCase`：系统对外提供的业务能力（输入端口）
  - `ValueObject`：承载单一业务概念的不可变值对象

二者核心理念一致：**代码标识符 = 业务语言**；区别是FunPark目前只建模领域内核，Java项目补齐完整应用层、适配器分层契约。

# 4. 本章没有复杂高阶抽象，为什么FP建模依然优先「数据优先」而不是行为优先？对比传统OOP实体
1. **FP核心思想：数据和行为分离**
把**数据（struct）** 和**操作该数据的纯函数**拆开；结构体只是被动的数据容器，所有业务逻辑是独立的纯函数，接收数据，返回一份全新的数据。

2. **可观测、可序列化、可持久化**
数据优先的设计，领域结构直白透明，方便打印日志、存入数据库、事件序列化，适合事件溯源这类架构。

3. **行为可以自由组合**
函数独立，可以单独测试、复用、流水线组合（管道模式）；不需要把方法绑定在实体上。

对比传统OOP：
OOP是**对象包裹数据+内部行为**，行为依附在实体上；调用形式为 `patron.grant_fastpass()`；
FP调用形式为 `FunPark.Patron.grant_fastpass(patron, fastpass)`。

- OOP：**行为属于对象**
- FP：**行为是独立函数，数据作为参数传入**

# 一句话总结本章核心思想
> FP‑DDD 建模：先用不可变数据描述现实世界业务概念，再用独立纯函数描述业务规则与变更；
> OOP‑DDD：把数据和业务行为封装到同一个实体内部；
> Java混合范式（Tom六边形架构）：折中方案，实体承载基础数据，复杂业务逻辑下沉到领域服务。
