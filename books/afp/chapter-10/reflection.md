## 1. Effect 的本质是什么？它和单纯 Lazy（延迟求值）、Either（错误处理）各自负责什么能力，Effect 整合了二者哪些特性？

**答案**

- `Lazy`：只负责**延迟计算**，不处理异常，不描述 IO，只推迟求值时机。
- `Either`：只负责**成功 / 失败双通道结果**，是执行完成之后的值，本身不具备延迟能力。
- `Effect` = **延迟执行的可失败任务描述**，同时封装两件事：
  1. 延迟（不会立刻运行 IO）
  2. 内置失败通道（类似 Either）
- Effect 把「一段带副作用、可能失败的动作」变成一个**普通的值**，可以 map /flatMap 自由编排，最后在边界一次性运行。

> 
> 一句话：Lazy 管时机，Either 管结果，Effect 两者全包，再加 IO 语义。

---

## 2. 为什么要把 IO / 副作用动作包装成 Effect，而不是直接执行函数？这种设计对业务代码的可测试性带来了什么好处？

**答案**

1. 如果直接执行 IO：一旦调用函数，数据库、消息发送立刻发生，单元测试无法隔离外部依赖。
2. Effect 只是**描述动作，而不是执行动作**。
   - 业务逻辑只组装 Effect 管道，不触发真实 IO；
   - 测试阶段我们可以替换执行器或者替换存储端口，使用内存实现；
   - 真实副作用推迟到最外层适配器执行。
3. 测试收益：UseCase / 应用编排代码完全不需要启动真实基础设施，业务逻辑可以做纯单元验证。

---

## 3. 描述「定义 Effect」和「执行 Effect」两个阶段的区别；为什么业务流程只做 Effect 描述，推迟到最后一步才真正运行 IO？

**答案**

- **定义阶段（构建管道）**：使用 `map / flatMap` 拼接一系列 IO 动作，返回一个 Effect 数据结构；**此时没有任何读写发生**，只是一份任务清单。
- **执行阶段（run）**：在程序最外层（Adapter / Main）调用执行函数，依次运行所有副作用。

推迟执行的架构价值：

1. 先完成全部**纯领域校验**，确认业务合法之后再触碰外部资源；
2. 可以批量收集副作用，统一在事务边界提交；
3. 如果中间业务校验失败，后面所有 IO 直接取消执行，避免脏写。

---

## 4. 对比你之前实现的**延迟领域事件模式**：Effect 和内存收集领域事件，底层思想为什么是同源的？差异点在哪里？

**答案**
✅ **同源思想**：
都是「**先在内存收集要执行的动作，业务全部校验通过之后，在事务成功之后统一执行副作用**」。
UseCase 不立刻发送事件，而是暂存事件列表。

🔎 **差异**

- 延迟领域事件：只是简单内存集合（`List<DomainEvent>`），只能追加事件，**不能链式编排复杂失败逻辑**。
- Effect：是可组合的 Monad 结构，可以表达顺序依赖、失败中断、多步骤 IO 流水线，能力更强。

> 
> 延迟领域事件 = Effect 的一个最简单特例。

---

## 5. DMMF 只提出「IO 放在外层执行」的原则；Effect 更进一步，把副作用变成可以组合、链式拼接的值。请对比这套思想和 Java 中「延迟领域事件、事务发件箱模式」的异同。

**答案**

- DMMF：**原则约束**，领域层禁止 IO，副作用交给外层；但是没有提供语法构件去编排一系列 IO 动作。
- Java 延迟事件 / 发件箱：**数据收集模式**，收集事件 / 待持久化记录，事务成功后批量执行；适合事件发布、追加存储。
- Effect：**可编程的任务流水线**，每一步 IO 依赖上一步结果，可以中途失败终止流程，适合复杂多步骤外部调用。

相同点：纯业务在前，副作用后置执行；
区别：发件箱是静态列表；Effect 是动态可分支、可失败的计算图。

---

## 6. 在我们既定的 Java‑Spring‑Vavr 技术栈里，我们不会完整复刻一套自定义 Effect Monad。我们可以用 Vavr/Java 原生哪些工具、设计模式模拟 Effect 这套「先描述，后执行」的编程思想？各自的局限是什么？

**答案**
可用来模拟的工具与模式：

1. `Supplier<T>` / `Callable<T>`：实现延迟；但缺少内置错误通道，无法链式优雅处理失败。
2. `Lazy<T>`（Vavr）：延迟求值；只能存成功结果，不自带 Either 错误处理。
3. `Either<Error, T>`：处理失败；**不是延迟的，执行即得到结果**。
4. 自定义命令对象模式（Command Object）：把副作用封装成对象列表，最后循环执行；对应延迟事件 / 发件箱。
5. `CompletableFuture`：延迟异步任务；偏重并发，不是领域编排语义。

**局限总结**
Java 生态没有原生一体化 Effect 类型；生产项目我们**不造完整 Monad**，采用混合方案：

- 领域：纯函数返回事件列表
- 应用层：收集待执行操作
- 基础设施层：事务提交后批量执行

## 7. 严格分层边界辨析：Domain 层 / Application 应用层 / Adapter 基础设施层各自在 Effect 流程里承担什么职责？为什么 Domain 内部永远不允许出现 Effect？

**答案**

1. **Domain（领域核心）**：只包含纯业务规则、状态转换；返回新状态和领域事件；**不定义 Effect，不描述 IO**。领域必须保持无副作用、可独立单元测试。
2. **Application（UseCase）**：编排业务流程，把领域输出转化为一系列 Effect / 待执行操作；负责组装任务管道，但**依然不真正运行 IO**。
3. **Adapter（基础设施）**：唯一负责执行 Effect、调用数据库、消息队列；Spring 事务、真实外部交互全部放在这一层。

Domain 禁止 Effect 的根本原因：领域逻辑不能绑定任何外部技术实现，保证业务规则独立于存储、消息等基础设施。

## 8. 一条完整的事件溯源命令处理链路，请拆分成「纯领域计算片段」和「Effect 副作用片段」，描述整条执行顺序。

**完整链路拆分**

1. 【Effect‑执行】从事件存储读取聚合历史事件（IO）
2. 【纯领域计算】fold 折叠事件，还原聚合当前状态（无副作用）
3. 【纯领域计算】执行命令校验，产生新的领域事件集合（无副作用）
4. 【Effect‑描述】定义追加事件写入事件库的任务（仅描述）
5. 【Effect‑描述】定义发布集成事件到消息队列的任务（仅描述）
6. 【Effect‑执行】事务成功之后，批量运行持久化与消息发送的副作用

> 
> 2、3 两步是纯 Domain；1、4、5、6 是 Effect 相关 IO 动作。

## 9. Effect 范式：先批量构造 Effect 列表，事务提交成功之后统一持久化、发布事件。这套思路，可以从哪些角度反向优化我们现有的 Java UseCase 实现？

**答案（Java 落地优化点）**

1. 彻底分离：UseCase 业务逻辑**不要在行内直接调用 Repository 保存**；先完成全部领域计算，收集变更和事件；事务边界统一后置执行。
2. 保证原子性：只有全部业务校验通过，才触发持久化与消息发送；校验失败不会产生任何残留 IO。
3. 可测试提升：UseCase 单元测试只断言产生的事件列表，不需要 mock Repository；真实存储逻辑交给集成测试验证。
4. 为发件箱模式预留扩展点：收集后的操作可以选择本地内存执行，或者写入发件箱表异步投递。

## 10. Effectful Store（可替换存储抽象）和六边形架构的输出端口（Secondary Port）在设计理念上是不是一致？测试时如何利用这种抽象切换内存实现和持久化实现？

**答案**
理念**完全一致**。

- Effectful Store：定义存储的抽象契约，提供内存实现和持久实现；
- 六边形 Secondary Port：接口作为抽象契约，InMemory 替身用于单元测试，Jdbc 实现用于生产。

使用方式：

- 应用层只依赖抽象端口，不绑定具体技术；
- 单元测试注入 InMemory 实现；
- Spring 生产环境注入真实数据库实现。
Effect 只是 Elixir 用来编排调用这个端口的工具，端口抽象本身就是六边形的核心思想。

## 11. 在 Spring 六边形业务项目中，哪些场景值得使用「Effect 风格的延迟编排」，哪些场景保持直接调用 Repository 的简单写法就足够？什么时候引入这种抽象属于过度设计？

**答案**
✅ **适合延迟编排（Effect 思想）的场景**

- 事件溯源命令处理流程
- 一条业务触发多个外部系统调用、多条消息发布
- 需要先完整校验全部业务规则，成功之后统一提交事务和副作用
- 希望 UseCase 单元测试完全脱离外部依赖

✅ **直接调用 Repository 更简单（不引入复杂抽象）**

- 普通 CRUD 短流程用例：校验 → save；步骤极少，业务简单
- 追求代码直白可读，团队维护成本优先

> 
> 判定原则：流程短、依赖少，直接调用；流程复杂、多副作用、强测试需求，采用后置批量执行的 Effect 风格。**不为了 FP 而 FP**。

## 12. Effect 可以实现任务的顺序编排、失败中断；对比 Spring 事务管理机制，二者职责如何分工共存？

**答案**

- **Effect / 应用编排层**：控制业务逻辑分支、判断哪些副作用需要执行，定义任务依赖顺序；决定「要不要执行 IO」。
- **Spring 事务**：控制数据库的原子提交 / 回滚；管理资源连接，保证写入的 ACID 特性。

分工示例：

1. Effect 管道确认业务合法，生成待持久化事件集合
2. Spring 开启事务
3. 在事务内部执行存储写入
4. 事务提交后执行消息发送等最终副作用

Effect 负责**业务任务编排**；Spring 负责**底层资源事务保障**，二者互补，互不替代。

**总结笔记（可直接复制）**
Effect 的核心架构思想是**分离描述与执行，分离纯领域逻辑与副作用**。业务代码只定义要做什么，推迟 IO 执行到最外层适配器。这套范式和六边形架构、延迟领域事件、发件箱模式高度契合。在 Java‑Spring 混合范式中我们不需要完整实现 Effect Monad，而是借鉴它后置执行副作用的设计原则，保证 Domain 纯净、UseCase 易于测试，在复杂事件驱动业务中获得更好的可维护性。
